依赖更新这件事，手动做很容易拖延——每个包都要自己查有没有新版本、有没有安全漏洞，几十个依赖根本盯不过来。但如果你仔细翻过 GitHub 的仓库设置，会发现有一个叫 **Dependabot** 的东西，它是 GitHub 平台自带的、不需要额外付费就能用的依赖管理服务。

这篇文章记录了我发现并使用它的过程：从“这啥？”到“真香”，再到认识到了这种自动化工具对日常开发的帮助、慢慢把它变成了自己项目里常驻的习惯。

## 一、它到底是什么

---

先说一个容易误解的点。当时我发现远程仓库上突然多出来俩个不认识的分支，名字类似 `dependabot/bun/production-dependencies-xxx`，但我自己并没有创建过它，起初还以为是 Fork 的上游仓库自带的，后来查了资料才弄清楚：

**Dependabot 是 GitHub 平台内置的依赖管理服务，适用于 GitHub 上的所有仓库。** 你不需要在项目里写任何执行代码，只要仓库里存在 `.github/dependabot.yml` 这个配置文件，GitHub 服务器就会在后台按配置定期扫描依赖、自动创建 PR。

上游仓库的[作者](https://github.com/dodolalorc/astro-navfolio)写了这份配置文件，才把这个功能“激活”了。只要文件存在于仓库中，GitHub 引擎就会按规则自动干活；换成任何其他的 GitHub 仓库，放上同样的文件，都能获得完全一致的效果。

## 二、dependabot.yml 配置文件

---

以本项目为例：

```yaml
version: 2
updates:
  - package-ecosystem: 'bun'
    directory: '/'
    schedule:
      interval: 'weekly'
    groups:
      production-dependencies:
        applies-to: 'version-updates'
        patterns:
          - '*'
  - package-ecosystem: 'github-actions'
    directory: '/'
    schedule:
      interval: 'weekly'
    groups:
      ci-dependencies:
        applies-to: 'version-updates'
        patterns:
          - '*'
```

**`package-ecosystem`（扫描生态）**
这告诉 Dependabot 去扫描哪种类型的依赖文件。
* 第一个任务配置了 `'bun'`，Dependabot 就会去读取项目根目录下的 `package.json` 和 `bun.lock`。GitHub 官方确认支持 Bun（需 >= v1.1.39）。如果你的项目用 `npm` 或 `pnpm`，这里对应改成 `'npm'` 或 `'pnpm'` 即可。
* 第二个任务配置了 `'github-actions'`，专门负责扫描 `.github/workflows/` 里的自动化脚本依赖。

**`directory: '/'`（扫描目录）**
告诉 Dependabot 去哪里找上述的配置文件。`'/'` 代表项目的根目录。如果你的项目是 Monorepo（比如前端在 `frontend/`，后端在 `backend/`），这里就需要分别写 `'/frontend'` 和 `'/backend'`。

**`schedule.interval: 'weekly'`（检查频率）**
这是扫描的周期。可选值包括 `daily`、`weekly`、`monthly`。每周一次对我刚好：PR 不会多到烦人，也不会漏掉重要的安全更新。

**`groups`（合并更新，管理 PR 数量）**
这是真正让 PR 数量变得可管理的核心配置。默认情况下，Dependabot 会为每个依赖单独开一个 PR。如果有几十个依赖同时更新，PR 列表会瞬间被淹没。`groups` 配合 `patterns: ['*']`，能把“本次扫描的周期内”所有匹配的生产依赖（或 Actions 依赖）打包进一个 PR，你只需要集中 review 一次、合并一次，极大地减轻了维护负担。

实际收到的 PR 标题长这样：

```text
Bump the production-dependencies group with .... updates
```

点开是一张表格，列出每个包从哪个版本升到哪个版本，附带的 release notes 和 changelog 链接也自动整理好了。不需要自己去 npm 或 GitHub 上逐个翻。

## 三、带来的好处

---

它把依赖管理从一件靠人记、靠自觉的事，变成了一个有节奏、有记录、可追溯的系统流程。

**符合 SemVer 的升级节奏。** Dependabot 在发起 PR 时会直接注明依赖版本“由几变成了几”。根据 SemVer 的约定，如果只是小版本的修补（比如 8.72.0 变成 8.72.1），理论上都是兼容的，可以快速放行；但如果跨度特别大，跨越了主版本号，就极有可能包含破坏性变更。这就提醒我，面对这种大跨度更新，合并后绝不能“无脑点 Merge”，必须跑一遍完整的构建验证才算稳妥。

**符合“小步快跑”的工程原则。** 如果项目依赖经常不升级，之后想升级一个包，结果发现它依赖的另一个包也得升，另一个包又依赖别的……最后带来的成本较高。每周小步升级，每次只动几个版本号，验证面很小，出问题也容易定位。

**符合“关注点分离”的协作习惯。** Dependabot 的 PR 只改 `package.json` 和 `bun.lock` 两个文件，零业务代码改动。review 成本极低，回滚也干净——`git revert` 一下就行，不牵扯任何逻辑。

**和 CI 天然配合。** 本站的部署 workflow 只在 push 到 `v1` 分支时触发。Dependabot 的 PR 本身不会触发部署，合并之后才会。这给了你一个天然的“合并前先本地验证”的缓冲期。

## 四、如果不用 GitHub，能不能达到类似效果？

---

Dependabot 的机制并不神秘，拆开看就三件事：

1. 读取依赖清单文件（`package.json`、`bun.lock`、`pyproject.toml` 等）
2. 对比上游 registry 的最新版本
3. 有差异就创建分支、提交变更、开 PR

GitHub 把这三件事做成了托管服务，所以你什么都不用写。但同样的逻辑，你完全可以自己在非 GitHub 环境里复现。

**思路一：用现成的开源替代品。** 比如 [Renovate](https://docs.renovatebot.com/)，它支持的平台比 Dependabot 更广——GitLab、Bitbucket、Gitea 都能用。核心逻辑一模一样：读配置、扫依赖、开 MR/PR。如果你从 GitHub 迁移到 GitLab，在项目根目录放一个 `renovate.json`，接上 CI 就能获得几乎相同的体验。

**思路二：自己写一个最小实现。** 如果你只用 CI 而不想引入第三方服务，在 CI 配置里加一个定时任务即可。伪代码大概长这样：

```yaml
# .gitlab-ci.yml 或任意 CI 的定时任务
update-deps:
  schedule: "0 9 * * 1"   # 每周一早上 9 点
  script:
    - bun update --latest   # 或 npm update，取决于你的包管理器
    - git checkout -b deps/auto-update
    - git commit -am "chore: auto update dependencies"
    - git push origin deps/auto-update
    # 再调用平台的 API 创建 MR/PR
```

关键是最后一步：需要调用平台 API 创建 MR，并附上版本变更信息。没有 Dependabot 那么精致（不会自动抓 changelog、不会分组、不会标注 SemVer 类型），但“自动化发现 + 人工审核合并”的核心流程是跑通的。

## 五、总结与思考

这套分工跑下来，依赖更新既不会拖延，也不会出事。Dependabot 比我勤快，但它不会替我做决定——自动化负责发现，人负责判断和收尾，这个边界保持住，工具才真正有用。
